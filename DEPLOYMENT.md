# Deployment status and guide

## Status

**Not deployed.** This repository now contains a Render Blueprint for the
Express/EJS web service, but no Render service or Oracle Cloud VM has been
created or tested. The current session has no Render deployment credential,
OCI CLI/configuration, or SSH access to an Oracle instance. GitHub access
alone does not provision either provider.

The Phase 6 local application implementation uses the OnlineCompiler.io
managed API for the Python coding assessment and requires its key to be
configured server-side. This is not an Oracle-hosted gVisor runner or a
verified deployment of the app-to-runner broker design below.

The working tree also contains existing uncommitted application changes.
Render auto-deploy is disabled in `render.yaml`; do not publish or deploy this
tree until its full diff is reviewed and intentionally pushed.

## Render web application

`render.yaml` defines one Node web service in Singapore on the Free plan:

- Build: `npm ci`
- Start: `npm start`
- Health: `/health/ready` (requires a working MongoDB connection)
- `SESSION_SECRET`: generated by Render
- `MONGODB_URI`: entered as a secret in the Render dashboard
- `TRUST_PROXY=true`: trusts exactly one Render ingress proxy hop for secure
  cookies and client address handling (not arbitrary forwarded headers)
- Automatic deploys: disabled; deploy manually after review

To provision it, push the reviewed repository to its GitHub remote, choose
**New > Blueprint** in Render, select the repository and `render.yaml`, then
enter `MONGODB_URI` in Render's environment settings. Never commit `.env` or
copy its values into this document. Keep `AI_API_KEY` unset unless the hosted
assistant is intended to make paid/usage-metered third-party calls.

In MongoDB Atlas, create a database user with only the required application
database permissions. Add the exact Render service outbound CIDR ranges shown
under its **Connect > Outbound** panel to Atlas Network Access; do not make
Atlas reachable from `0.0.0.0/0`. Confirm the Atlas tier and usage limits
before enabling public traffic.

Render's Free web service sleeps after 15 minutes without traffic, has an
ephemeral filesystem, and is not recommended by Render for production. The
free allowance and network/build quotas are limited; excess usage can suspend
service or incur charges depending on workspace billing settings. Therefore
this is a best-effort hobby deployment, not a guaranteed always-on or
unconditionally ₹0 production service. Keep workspace spending limits at
zero and check current usage/pricing before provisioning.

## Oracle Cloud runner feasibility

Oracle documents Always Free Ampere A1 compute up to 2 OCPUs and 12 GB memory
per month in the tenancy's home region. gVisor officially supports ARM64 and
Linux 5.6+, so an Ubuntu A1 VM is a technically compatible candidate. This
does not guarantee capacity in the selected region: Oracle may report
`out of host capacity`, and idle Always Free instances can be reclaimed.
Neither VM availability nor gVisor execution has been tested from this
workspace.

The VM must not expose a code-execution HTTP port to the internet. Oracle
network rules should allow only administrator SSH from a restricted source
address, and the runner process should have no public listener. Sandboxed
submissions must have no network, host mounts, cloud/database credentials, or
access to the Docker/OCI control socket.

### Application-to-runner connection constraint

Render Free services cannot receive private-network connections. Because the
runner is on Oracle rather than Render, a direct private Render-to-Oracle
connection is not available on this plan. The proposed no-public-runner
pattern is for an Oracle-side agent to initiate outbound HTTPS polling to a
small authenticated broker on the Render application. This keeps the runner
API unexposed, but it requires a replay-resistant runner identity, bounded
jobs/results, queue/lease recovery, and a verified gVisor execution service.
**No broker, runner client, or code-execution service currently exists.**
Consequently, secure runner communication is not configured and no student
code is executed.

Do not substitute an unauthenticated public endpoint, a public Docker socket,
direct execution by Express, or an ordinary child process. Do not send real
student source to an external execution provider as a workaround.

## Required live verification before claiming deployment

1. Deploy the reviewed Blueprint and verify the HTTPS home page, registration,
   session cookie flags, and `/health/ready` against Atlas.
2. Verify Atlas records and Render logs contain no credentials; verify account
   registration and session persistence after a service restart.
3. Provision an eligible Always Free ARM64 VM only after confirming the
   tenancy, region capacity, and quota. Record the OS/kernel/architecture and
   verify `runsc` version plus a benign gVisor smoke test.
4. Implement and review the outbound-only authenticated broker/runner before
   connecting services. Verify the Oracle VM has no public runner listener and
   that invalid/replayed runner messages are rejected.
5. Only then run synthetic sandbox tests for time, memory, process, filesystem,
   output, and network limits. Do not use production student data for these
   tests.

This deployment preparation does not implement Phase 8.
